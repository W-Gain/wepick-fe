## 목적

화면 구현을 계속 진행하면서 구조를 한 번에 다시 쓰지 않고, 변경하는 기능의 경계를 함께 정리하기 위한 계획입니다. 적용 시점과 완료 조건, 구체적인 코드 배치와 테스트 구현을 FE 저장소에서 함께 관리합니다.

## 현재 적용한 기준

### API 응답과 화면 모델 분리

화면은 서버 DTO를 직접 사용하지 않습니다.

```text
HTTP 응답
  → feature/responseAdapters.ts
  → shared/contracts의 화면 모델
  → query hook
  → screen/component
```

- `shared/api/client.ts`는 HTTP 처리만 담당합니다.
- 각 feature의 `responseAdapters.ts`가 응답 검증과 DTO 변환을 담당합니다.
- Mock 응답은 현재 화면 모델과 같은 형태이므로 schema 검증만 수행합니다.
- 현재 BE를 연결할 때 `/topics`, `/users` DTO schema와 변환 함수를 adapter에 추가합니다.
- 현재 BE 필드가 부족해도 화면 모델이나 컴포넌트에 임시 필드를 퍼뜨리지 않습니다.

### 인증과 로그인 복귀 의도 분리

`AuthFlowProvider`는 인증 상태와 로그인 후 재개할 행동을 보관하는 최소 경계입니다. 복귀 정보에는 행동 종류, 원래 URL, 대상 ID와 작성 중인 내용이 포함될 수 있습니다.

현재는 카카오 OAuth와 세션 확인 API가 연결되지 않았으므로 메모리 상태만 제공합니다. 인증 상세 설계와 실제 OAuth를 연결할 때 다음을 이 경계 안에서 결정합니다.

- 앱 시작 시 세션 확인과 `unknown → anonymous/authenticated` 전환
- 외부 인증 이동을 견디는 복귀 정보 저장 방식과 만료 시간
- 로그인 성공 후 익명 투표 연결, 원래 URL 이동과 행동 재개
- 취소·실패·만료 시 복귀 정보를 폐기하는 기준

화면 컴포넌트는 로그인 URL이나 저장소를 직접 다루지 않고 `LoginIntent`만 전달합니다.

### 처리 결과 알림

토스트는 FIFO 대기열에서 한 번에 하나만 표시합니다. 같은 제목과 설명의 대기 중 알림은 중복 추가하지 않습니다. 시트나 다이얼로그가 열리면 토스트 표시를 중지하고, 해당 오버레이가 닫힌 뒤 남아 있는 알림을 이어서 표시합니다.

오버레이 안에서 발생한 진행·실패는 토스트로 만들지 않고 오버레이 내부 상태로 표시합니다.

## 기능 개발과 함께 진행할 구조 개선

아래 작업은 별도 전면 리팩터링으로 진행하지 않습니다. 관련 기능을 실제 API에 연결하거나 동작을 추가하는 PR에서 함께 적용합니다.

| 변경 대상                 | 함께 정리할 내용                                      | 완료 판단                                                 |
| ------------------------- | ----------------------------------------------------- | --------------------------------------------------------- |
| Pick 조회·투표·의견       | `PickScreen`에서 헤더, 투표, 결과, 의견 영역 분리     | 각 영역이 독립 props를 받고 API hook을 직접 호출하지 않음 |
| 현재 BE 연결              | Topic/User DTO schema와 adapter 구현                  | 화면에서 DTO 필드명과 현재 BE 예외 조건을 사용하지 않음   |
| 카카오 로그인             | 인증 상태 조회, OAuth 시작·복귀, `LoginIntent` 영속화 | 새로고침과 외부 인증 후에도 원래 행동을 안전하게 재개     |
| 프로필 저장·이미지 업로드 | 로컬 cache 성공 처리 대신 mutation과 오류 매핑 적용   | 서버 성공 후 cache 갱신, 실패 시 입력 유지                |
| 의견 작성·수정·삭제·공감  | mutation별 상태와 cache 갱신을 feature 단위로 분리    | 중복 요청 차단과 실패 복구가 화면 정의서 상태와 일치      |
| 목록 추가 로딩            | 페이지 상태와 스크롤 복원 분리                        | 지난 Pick과 내 기록이 같은 페이지 처리 원칙 사용          |
| 스타일 변경               | 변경하는 화면의 CSS를 화면·컴포넌트 단위로 이동       | 사용하지 않는 전역 selector를 함께 제거하고 토큰은 유지   |
| 로그인 필요 화면          | 내 기록·프로필 route 접근 제어 추가                   | 비로그인 진입 시 OVL-001, 로그인 후 목적 화면 복귀        |

공통 컴포넌트는 두 곳 이상에서 실제로 같은 동작과 상태를 공유할 때만 추출합니다. 이름이나 외형이 비슷하다는 이유만으로 먼저 일반화하지 않습니다.

## PR 확인 항목

기능 PR에서는 다음을 확인합니다.

1. Product 화면 ID와 상태 중 이번 PR이 구현하는 범위를 PR 설명에 연결합니다.
2. 서버 응답 변경은 adapter와 계약 테스트에서 먼저 드러나게 합니다.
3. 화면에서 API URL, 서버 DTO 필드명과 인증 저장 방식을 직접 사용하지 않습니다.
4. 성공·빈 상태·오류·처리 중 상태 중 영향을 받는 상태를 검증합니다.
5. 변경한 기능의 컴포넌트와 CSS가 과도하게 커졌다면 같은 PR에서 해당 경계만 분리합니다.
6. `typecheck → lint → test → build`를 통과합니다.

## 현재 남은 제한

- `AuthFlowProvider`의 인증 상태는 아직 실제 세션과 연결되지 않았습니다.
- 로그인 복귀 정보는 외부 OAuth 이동을 견디도록 영속화되지 않았습니다.
- Mock/목표 화면 계약 adapter만 있으며 현재 BE Topic/User DTO adapter는 4단계 작업입니다.
- `PickScreen`과 `global.css`는 아직 큰 편이며 관련 기능을 구현할 때 점진적으로 나눕니다.
- 핵심 모바일 흐름의 브라우저 통합 테스트와 320~430px 반응형 검증은 별도 일정으로 남아 있습니다.
